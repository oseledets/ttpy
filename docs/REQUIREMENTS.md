# ttpy2 — требования

Документ — источник истины. Код можно снести и перегенерировать по этому файлу и тестам.

## R0. Зачем

`ttpy` (2024) не собирается и не запускается на современной машине:

* ядро и половина алгоритмов — Fortran (`tt-fort`, `amen_f90`, `tt_f90`, `tt_eigb`,
  `tt_ksl`, `maxvol.f90`, `cross.f90`), сборка требует `gfortran` + `f2py` +
  numpy.distutils, которого нет в numpy >= 1.26;
* три сабмодуля, два из них на bitbucket;
* Python-код использует `np.float`, `np.complex` (удалены в numpy 1.24),
  `six.moves`, `d is 2` (сравнение int через `is`).

Цель: **та же математика, ноль компиляции, быстрее, `pip install` за секунды.**

## R1. Установка

* Чистый Python-пакет. Никакого Fortran/C/f2py/cmake. Wheel — `py3-none-any`.
* Обязательные зависимости: `numpy`, `scipy` (обе — готовые wheel).
* GPU опционален: `pip install ttpy[torch]`. Отсутствие torch не ломает импорт.
* Критерий приёмки: в пустом venv `uv pip install .` завершается без компилятора,
  `python -c "import tt; tt.rand(2,10,3).round(1e-8)"` работает.

## R2. Совместимость API

Старые скрипты `import tt` должны работать без правок. Сохраняются:

* `tt.vector` (`tt.tensor` — deprecated alias), `tt.matrix`;
* атрибуты `d, n, r, core, ps, erank, is_complex`;
* `from_list / to_list / full / round / norm / copy / write`,
  арифметика `+ - * kron dot diag`, `__getitem__` со срезами;
* `tt.ones/rand/eye/xfun/linspace/sin/cos/delta/stepfun/unit/qshift/IpaS/
  Toeplitz/qlaplace_dd/kron/mkron/zkron/zkronv/zmeshgrid/zaffine/concatenate/
  sum/reshape/permute/matvec/col/diag/dot`;
* `tt.multifuncrs, tt.multifuncrs2, tt.GMRES`;
* `tt.amen.amen_solve, tt.amen.amen_mv, tt.eigb.eigb, tt.ksl.ksl,
  tt.ksl.diag_ksl, tt.cross.*, tt.maxvol.maxvol, tt.optimize.tt_min.*,
  tt.riemannian.*, tt.completion.*`.

**Внутреннее представление меняется.** Владелец истины — `cores: list[ndarray]`
формы `(r_k, n_k, r_{k+1})`. Плоский `core` и указатели `ps` — производные
свойства (совместимость), а не хранилище. Присваивание `x.core = buf`
пересобирает `cores` (конвертер, не второй владелец).

## R3. Бэкенды

* Один код для numpy и torch. Диспетчер — единственный владелец знания «как
  сделать svd/qr/matmul/dtype» (`tt/backend.py`).
* `tt.set_backend("numpy" | "torch", device=..., dtype=...)`.
* Ядра внутри одного тензора всегда одного бэкенда и dtype; смешение — громкая
  ошибка, не тихое приведение.

## R4. Численность

* По умолчанию float64 (complex128 для комплексных).
* Точность округления: `round(eps)` даёт относительную ошибку Фробениуса
  <= `eps` для точно представимых сумм; проверяется на плотной истине.
* Допуски тестов: не жёстче `4 * eps(dtype) * масштаб`.
* Неожиданное состояние (несходимость, ранг > rmax при заданной точности,
  сингулярная локальная задача) — явная ошибка или предупреждение с числом,
  а не тихая подстановка правдоподобного ответа.

## R4a. QTT для эллиптических задач (новое в 2.0)

Не легаси-совместимость, а новая возможность. Владелец — `tt/algs/qtt_ell.py`
плюс четыре конструктора в `tt/core/tools.py`.

* Конструктор: `qdiff` (разностный оператор `I - S`, ранг 2), `qtri_ones`
  (его **точный** обратный, ранг 2), `qlaplace_dn(d, bc, order)` со смешанными
  краевыми условиями, `level_major_order`.
* `bc='DN'` — единственная комбинация с ровно `2^l` степенями свободы на
  уровне, поэтому только она годится для многоуровневых продолжений;
  `qlaplace_dd` для этого непригоден. `bc='NN'` вырожден и **отклоняется**.
* Порядок индексов — явный аргумент, не умолчание: оценки рангов
  предобуславливателя верны только в **level-major** раскладке, а `kron` и
  `qlaplace_dd` дают dimension-major. Оператор и предобуславливатель в разных
  раскладках перемножаются в бессмыслицу молча, поэтому ни одна из них не
  должна выбираться случайно. `merge_levels` — единственный владелец перевода.
* `bpx(d, D, weight, scaled)` — предобуславливатель BPX ([BK20], Теорема 3),
  собранный как двухсостоянийный автомат по уровням: **без суммирования**
  TT-матриц и без округления. Ранг ровно `2*4^D`, независимо от `d`.
* `bpx_theta(d, D)` — слитные множители ([BK20] Лемма 5 / Теорема 4),
  `B = sum_k Theta_k^T Theta_k`, ранг `2^(2D) + 2^(2D-1)`. Возвращает **список**
  даже при `D = 1`: при `D > 1` сумму нельзя собирать, её применяют
  пофакторно.
* Критерий приёмки: `kappa(C A C)` ограничено при росте `d`, тогда как
  `kappa(A)` растёт как `4^d`. Проверяется плотными собственными числами.
* Переменный коэффициент не требует замкнутой формы: `1/a` и `sqrt(a)` берутся
  крестом (`tt.multifuncrs`), обёртки — `qtt_ell.invert` / `qtt_ell.sqrt`.
  Допуск креста становится допуском схемы, поэтому он в сигнатуре, а не внутри.

## R5. Оракул корректности

Легаси-код **не** является оракулом. Истина:

1. плотное вычисление в numpy для малых `d, n` (полный тензор, полное СЛАУ,
   полная задача на собственные значения, полный `expm`);
2. инварианты (ортогональность после свипа, `A x = b` с невязкой <= eps,
   монотонность энергии, ранги <= теоретических);
3. сравнение алгоритмов между собой (`amen_solve` vs `GMRES` vs плотный solve).

Каждый алгоритм закрыт тестом против (1) или (2).

## R6. Скорость

Замер всегда вместе с режимом: бэкенд, устройство, dtype, число потоков, размер
задачи, число повторов. Целевые сценарии:

* `round` / `full_to_tt` больших TT (n=2, d=30..60, r=50..400);
* `amen_solve` на qlaplace_dd(d) и Toeplitz;
* `cross` / `multifuncrs2` на функциях от QTT-сеток.

Сравнение: numpy(CPU, 128 ядер) vs torch(B300) vs исходный ttpy там, где его
удалось собрать.

## R7. Объяснимость

Все итерационные алгоритмы возвращают/логируют историю: свипы, невязки, ранги,
время. `verb=0` молчит, но история доступна программно.
